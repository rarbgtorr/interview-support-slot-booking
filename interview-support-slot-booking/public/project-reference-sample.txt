1 <Project Name> :

<Project Overview:>

I worked on a project called CPRA-TECH, where we developed a Request Broker to help customers exercise their data privacy rights, such as requesting to access, update, or delete their personal data.

One of the key achievements of this project was building a Python SDK that automates the complete request processing workflow. Instead of being tightly coupled to one implementation, the SDK is designed as a reusable library that other teams can use to build their own request brokers with minimal effort.

The request broker is divided into three major components:

#1. Consumer

The Consumer receives customer requests through an Amazon Kinesis Stream. Each event contains the Amazon S3 path of the actual request file, which includes detailed information about the customer's request.

The Consumer:

* Reads the request file from S3.
* Parses the request details.
* Stores the processed information into intermediate storage systems such as **Amazon S3, local storage, MySQL, Oracle, and DynamoDB**.

#2. Executor

The Executor is the core processing component.

Its responsibilities include:

* Reading request details from the intermediate storage.
* Automatically generating queries based on the request type.
* Fetching, updating, or deleting customer data from target databases such as MySQL, Oracle, and DynamoDB.
* Storing the processed results as CSV files back into the intermediate storage.

#3. Producer

The Producer retrieves the generated CSV files from the Executor and sends an acknowledgement or response back to the customer, indicating that the request has been successfully processed.

#SDK Architecture

A major advantage of our SDK is that it is loosely coupled and highly modular.

Teams can:

* Use our Consumer and Producer while developing their own custom Executor.
* Use only the Executor while implementing their own Consumer and Producer.
* Extend the SDK by adding support for new intermediate storage systems or additional target databases without affecting the existing components.

This modular architecture makes the SDK highly reusable, scalable, and easy to maintain.

#Project Reusability

We demonstrated the reusability of our SDK by building our first implementation called the Zendesk Broker. For this project, we reused the existing Consumer and Producer components and only developed a new Executor specific to Zendesk. This significantly reduced development effort and demonstrated the flexibility of our architecture.

* Integrating with Amazon Kinesis, Amazon S3, MySQL, Oracle, and DynamoDB.
* Ensuring the SDK was modular, reusable, and extensible.
* Supporting new broker implementations using the common SDK.
